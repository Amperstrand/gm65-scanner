## COMMENT #92 — discriminator data (stays open)

2026-09-11 session data (pose verified in-pocket, gate 6/6 same morning):

- **soak_diag (16/60)**: through the collapse `isr_overrun_errors`
  stayed 0, `scan_count` climbed to 143, `ring_len` flipped 0↔14 (bytes
  arriving unstaged), losses size-biased (≤14B mostly deliver, ≥24B
  mostly lost), and the surviving deliveries cluster on the 5s
  retrigger boundary — a stop/start cycle flushes the stuck path.
- **Fresh F469 boot delivers instantly** — including payloads that
  "failed" during the collapse (module had decoded and buffered them).
- **Async variant is a carryover choke**: after sustained sync load,
  fresh async boots gate-fail with uart_errors=19 (twice reproduced)
  until 0x22 heals from a fresh-boot state.

Reading: the delivery killer is firmware-side staging between the ISR
ring and the scan buffer under sustained load — not module death, not
UART overrun. Root-cause target: the `scanner_core`/`buffer` read/staging
path and its interaction with trigger cadence. Artifacts:
`tools/hil/results/soakdiag-20260911-*/`, LIMITATIONS.md §1 update.

## COMMENT #100 — Tier A negative (stays open, blocked on #92)

Validated 2026-09-11 with the pose known-good (A/B with built-in
control, `tools/hil/heal_validate.py`, artifacts in
`tools/hil/results/healval-*/`):

- 0xA5 (0x23): sent=1, **responsive=0** — module took the deep-sleep
  reboot but never re-answered ping in the firmware's ~1s window;
  sync delivery went OK→FAIL after it; the async choke was unchanged.
- 0x22 fallback: accepted, but reinit_ok=0 from the desynced state
  (module left at model=0); a second 0x22 from a fresh-boot firmware
  state healed it ([0,1,1], connected=1).

Tier A is not viable as implemented — either the wake handshake needs
characterization (longer settle? different probe?) or the tier is
dropped. Boot policy stays blocked on #92 regardless: the dominant
failure mode is firmware-side staging, which no module-side boot heal
touches. Full pack:
`docs/issue-drafts/2026-09-11-module-reboot-tier-a-negative.md`.

## COMMENT #94 — fix pushed (stays open until HW acceptance)

Fixed in 0e8132a: LINE_MAX was sized only for `QR <hex>` (3 + 2·250);
the envelope ladder drives `QRS <cap> <hex>` (8 overhead) and `QRP <x>
<y> <hex>` is 12 — now 12 + 2·PAYLOAD_MAX with the form enumeration in
the comment; protocol docstring documents the 250B cap for every form.
esp release build green. HW acceptance (250B cell renders; envelope
rerun reaches the 250B cell) deferred — bench flock held by another
session. Note: >92B/frame never decodes on this rig regardless, so the
fix is correctness-only.
